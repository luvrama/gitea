# Database Connection Pool Exhaustion: Impact Analysis & Error Propagation

## Architecture Context

Gitea uses a single XORM connection pool shared across all 475 API endpoints. There is:
- No read replicas configured by default
- No caching layer between the API and database
- No built-in API rate limiting
- No readiness probe that checks DB connectivity (only a version endpoint as basic liveness)
- No circuit breaker or retry logic for database operations

## Which Endpoints Are Affected

All 475 endpoints are affected. The database is a single point of failure documented repeatedly in the wiki:

│ "⚠️ Database (single connection pool)"  
│ "⚠️ Database - all endpoints depend on it with no caching layer"  
│ "⚠️ Database (single XORM connection)"

Every endpoint that performs any database operation (which is effectively all of them except GET /api/v1/version [ep-001]) will fail when the pool is exhausted.

## Error Propagation Path

The error propagation follows this chain:

XORM Connection Pool (exhausted/timeout)
  → XORM engine returns Go error (context deadline exceeded / connection timeout)
    → models/repository layer receives error, returns it unmodified
      → services layer propagates error upward
        → routers/controller layer catches error
          → Calls ctx.InternalServerError() or ctx.APIError()
            → HTTP 500 response with APIError JSON body


The global error handler in services/context/api.go maps errors to responses:

| Exception Type | HTTP Status | Response Format |
|---|---|---|
| internal_error | 500 | APIError JSON |
| generic error | 500 | APIError JSON |
| validation error | 422 | APIError JSON |
| not found | 404 | APIError JSON |

Notable exception: Notification count endpoint (ep-021, GET /api/v1/notifications/new) returns 422 instead of 500 on database errors, which is an inconsistency in error handling.

## How Endpoints Handle It

They don't handle it gracefully. The wiki documents for virtually every database-dependent endpoint:

- **Graceful degradation:** none
- **Retry:** ❌ missing
- **Circuit breaker:** ❌ missing
- **Fallback:** ❌ missing (for DB operations)

The only resiliency pattern present for the SQL Database (notification table) is:
- **Timeout:** ✅ (XORM default connection pool timeouts)
- **Bulkhead:** ✅ (connection pool itself acts as a bulkhead)

But there is no retry, no circuit breaker, and no fallback.

## Root Causes That Can Trigger Pool Exhaustion

Two documented cascading failure paths specifically lead to connection pool exhaustion:

### 1. ep-023: PUT /api/v1/repos/{owner}/{repo}/notifications (CRITICAL)

│ "ep-023 unbounded query can overload database, affecting all other endpoints sharing the connection pool"

- Performs db.Find without pagination (loads ALL matching notifications)
- Then executes ~8 DB round-trips per notification (SELECT+UPDATE for status, 4 SELECTs for LoadAttributes, 2 more for permission/comment)
- No transaction wrapping the loop — partial failures leave inconsistent state
- A user with thousands of notifications triggers thousands of queries in a single request

### 2. ep-127: GET /api/v1/users/{username}/activities/feeds (HIGH)

│ "Database overload from ep-127 N+1 queries → connection pool exhaustion → all API endpoints fail"

- Calls GetDoerRepoPermission individually for each action in the result set (N+1 pattern)
- 5+ queries per request under normal conditions
- Under load, saturates the connection pool

### 3. ep-192/ep-089: PUT /api/v1/user/blocks/{username} / PUT /api/v1/orgs/{org}/blocks/{username} (HIGH)

│ "Database slow → ep-192 BlockUser transaction holds locks for extended time → other write operations blocked"

- Long-running transaction touching multiple tables (follow, star, watch, issue_assignees, collaboration, repo_transfer)
- No timeout on the transaction
- Holds locks that block other write operations, causing connection pool starvation

## Cascading Failure Sequence

When pool exhaustion occurs:

1. Trigger: One of the above endpoints (or external DB slowness) exhausts available connections
2. Immediate impact: All new requests that need a DB connection block waiting for a free connection
3. Timeout: Requests eventually hit XORM's connection pool timeout
4. Error response: Each affected endpoint returns its error:
   - Most endpoints → HTTP 500 {"message": "internal error", "url": "..."}
   - Notification count (ep-021) → HTTP 422
   - Notification list (ep-019) → HTTP 500
5. UI impact: Notification badge broken, all API operations fail
6. No recovery mechanism: No circuit breaker to shed load, no rate limiting to prevent further requests, no health check to signal the system is degraded

## Summary of Missing Resiliency

| Pattern | Status | Impact |
|---|---|---|
| Connection pool timeout | ✅ Present | Prevents infinite blocking, but returns errors |
| Rate limiting | ❌ Missing | Cannot prevent pool exhaustion from request floods |
| Circuit breaker | ❌ Missing | Cannot fast-fail when DB is overloaded |
| Retry with backoff | ❌ Missing | Transient errors are not retried |
| Read replicas | ❌ Missing | All reads hit the same pool as writes |
| Query caching | ❌ Missing | Every request hits DB directly |
| Readiness probe | ❌ Missing | Load balancer cannot detect DB unavailability |
| Graceful degradation | ❌ Missing | No partial functionality when DB is slow |
