# Complete Notification System Map

## 1. Database Storage

### notification table

The primary storage for all notifications. Schema:

| Field | Type | Indexed | Description |
|-------|------|---------|-------------|
| id | int64 | PK, autoincr | Notification thread ID |
| user_id | int64 | Yes | Recipient user |
| repo_id | int64 | Yes | Associated repository |
| status | NotificationStatus (uint8) | Yes | unread, read, pinned |
| source | NotificationSource (uint8) | Yes | Source type (issue, PR, commit, repository) |
| issue_id | int64 | Yes | Associated issue/PR |
| commit_id | string | Yes | Associated commit (nullable) |
| comment_id | int64 | No | Associated comment (nullable) |
| updated_by | int64 | Yes | User who triggered the notification |
| created_unix | timeutil.TimeStamp | No | Creation timestamp |
| updated_unix | timeutil.TimeStamp | No | Last update timestamp |

### Supporting subscription tables

- **watch** — Repo-level subscription (determines who gets notifications for a repo)
- **issue_watch** — Issue-level subscription (explicit per-issue subscribe/unsubscribe)

## 5. Notification Flow Summary

Event occurs (e.g., PR merge)
    → Service layer calls notify_service
        → Determines recipients via:
            - watch table (repo watchers)
            - issue_watch table (issue subscribers)
            - Participation (commenters, assignees)
        → INSERT into notification table for each recipient
    → User polls GET /api/v1/notifications/new (ep-021)
    → User fetches GET /api/v1/notifications (ep-019)
    → User marks read via PUT /api/v1/notifications (ep-020) or PATCH .../threads/{id} (ep-025)
