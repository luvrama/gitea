# Complete Permission Checking Chain for the Gitea Repository API

Based on the wiki documentation, here is the exhaustive permission checking chain from request arrival to final allow/deny.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


## 1. Authentication (First Gate)

Every API request first passes through authentication. The wiki documents several auth modes:

Auth types observed across endpoints:
- bearer — Standard OAuth2/JWT bearer token
- token — API access token (personal access token)
- basic_or_reverse_proxy+token — For sensitive endpoints like token creation (ep-165)
- none — Public endpoints (e.g., repo search ep-362, version ep-001)
- bearer (admin required) — Admin-only endpoints (ep-098)
- optional — Public access allowed, but auth enhances results (ep-035)

Token Scope Validation:
Access tokens carry scopes that restrict operations. For example, ep-036 (delete all org repos) requires AccessTokenScopeCategoryRepository. The reqToken middleware validates that:
1. A valid token exists in the request
2. The token's scopes cover the requested operation

Key middleware: reqToken — Validates authentication token exists and is valid.

Business rule (ep-165): "Token endpoints require basic auth or reverse proxy auth (not token auth alone)" — meaning you cannot use a token to create another token.

## 2. Site Admin Bypass

Throughout the entire chain, site admins (user.IsAdmin = true) bypass almost all permission checks. This is documented consistently:

- reqOrgOwnership: "User is not site admin AND not org owner" (ep-057)
- reqOrgMembership: "User is org member or site admin" (ep-075)
- reqTeamMembership: "User is not site admin AND not org owner AND not team member" (ep-064)
- GetByID: Admin users see all repos regardless of access (ep-368)
- User blocks: "Admin users bypass block checks (IsUserBlockedBy returns false for admins)" (ep-192)

## 3. Organization-Level Permission Middleware

For endpoints under /orgs/{org}/..., the chain is:

### Step 3a: orgAssignment (Resolve Organization)

- Resolves org name from path parameter to a user record (type=Organization)
- Handles user redirects for renamed orgs
- Returns 404 if org doesn't exist
- Variants:
  - orgAssignment(true) — loads org by name
  - orgAssignment(false, true) — loads team by ID (for /teams/{id} endpoints)

Database: SELECT from user WHERE lower_name = ? AND type = Organization

### Step 3b: Organization Visibility Check

Before granting access, the system checks HasOrgOrUserVisible (ep-028):
- **Public orgs**: visible to everyone
- **Limited orgs**: visible to any authenticated user
- **Private orgs**: visible only to members and site admins

Database: SELECT from org_user WHERE uid = ? AND org_id = ?

### Step 3c: Permission Level Middleware (one of three)

reqOrgOwnership (most restrictive — for mutations):
- Condition: !ctx.IsUserSiteAdmin() && !IsOrganizationOwner(ctx, orgID, ctx.Doer.ID)
- Checks if user is in the "Owners" team via team_user+team table
- Returns 403 if not owner/admin
- Used for: create/edit/delete teams, edit org, delete org, manage runners/secrets/variables, manage org avatar, block users

reqOrgMembership (medium — for member-visible operations):
- Condition: User must be site admin OR org member
- Checks org_user table for membership
- Returns 403 if not member
- Used for: publicize/conceal membership, search teams, list team members

reqTeamMembership (least restrictive — for team-scoped reads):
- Condition: User must be site admin OR org owner OR member of the specific team
- Checks team_user/org_user tables
- Returns 404 (not 403) if not a member — hides team existence
- Used for: list team repos, list team members, view team activity feeds

## 4. Repository-Level Permission Resolution

For endpoints under /repos/{owner}/{repo}/..., the system builds a Permission context object.

### Step 4a: Repository Loading

The repo is resolved from {owner}/{repo} path parameters:
- **Database:** SELECT from repository WHERE owner_name = ? AND name = ?
- Loads repo attributes (owner, primary language)
- Returns 404 if not found

### Step 4b: GetDoerRepoPermission / GetIndividualUserRepoPermission

This is the core permission calculation function (ep-254 documents it in detail). It executes 4-6 DB queries:

1. LoadUnits — SELECT from repo_unit WHERE repo_id = ?
   - Determines which units (code, issues, wiki, PRs, projects, releases, packages, actions) are enabled

2. Site Admin Check — If user.IsAdmin, grant full access to all units → ALLOW

3. Owner Check — If user.ID == repo.OwnerID, grant owner-level access → ALLOW

4. Collaborator Check — SELECT from collaboration WHERE repo_id = ? AND user_id = ?
   - If user is a direct collaborator, their access level is stored in the collaboration record
   - Access levels: read, write, admin

5. LoadOwner — SELECT from user WHERE id = repo.owner_id
   - Needed to determine if repo belongs to an org

6. Organization Visibility Check — HasOrgOrUserVisible
   - If repo owner is an org, check if the doer can even see the org

7. Access Table Query — SELECT from access WHERE user_id = ? AND repo_id = ?
   - The access table stores pre-computed access levels
   - This is the materialized/denormalized permission cache

8. Team Permission Resolution (for org repos) — GetUserRepoTeams
   - SELECT from team WHERE org_id = ? AND id IN (SELECT team_id FROM team_user WHERE uid = ?)
   - For each team the user belongs to that has access to this repo, the effective permission is the maximum across all teams

### Step 4c: Unit-Level Permission

The final permission is not just a single access level — it's per-unit. Each unit can have a different access level based on team_unit configuration:

- CanWrite(unit.TypeCode) — Can user write to code?
- CanWrite(unit.TypeIssues) — Can user write issues?
- CanWriteIssuesOrPulls(isPull) — Can user write to issues or PRs?
- HasAnyUnitAccess() — Does user have access to at least one unit?
- IsOwner() — Is user the repo/org owner?
- IsAdmin() — Does user have admin access?

## 5. Access Level Hierarchy

Permission levels are cumulative (ep-028):

Owner > Admin > Write > Read > None


Mapped to perm.AccessMode constants:
- AccessModeOwner — Full control, can delete repo
- AccessModeAdmin — Can manage settings, branch protections, webhooks, collaborators
- AccessModeWrite — Can push code, create/edit issues, merge PRs
- AccessModeRead — Can view private repos, clone, read issues
- AccessModeNone — No access (or public-only access)

## 6. Endpoint-Specific Permission Checks

After the middleware chain establishes the permission context, individual endpoint handlers perform additional checks:

### Repository Admin Operations (ep-369 Edit Repo, ep-370 Delete Repo):
- **Delete:** user.IsAdmin || user.ID == repo.OwnerID || org.IsOrgAdmin(user.ID) → 403 if not
- **Edit:** Requires admin permission on the repo → 403 if not

### Collaborator Management (ep-252 Add Collaborator):
- Requires admin access to the repo (implied by endpoint registration)
- Additional check: user blocks prevent adding blocked users as collaborators
- Collaborator must be an active user account

### Branch Protection (ep-314 Create Branch Protection):
- Requires admin access to repo
- Whitelist users must have write access to code unit
- Approval whitelist users must have read access to PR unit

### Issue/PR Operations (ep-336 Add Labels):
- !ctx.Repo.Permission.CanWriteIssuesOrPulls(issue.IsPull) → 403

### Team-Repository Operations (ep-066 Add Repo to Team, ep-331 Add Team to Repo):
- ep-066: reqTeamMembership + admin-level access to the repository
- ep-331: !ctx.Repo.Owner.RepoAdminChangeTeamAccess && !ctx.Repo.Permission.IsOwner() → 403

### Mirror Sync (ep-234):
- !ctx.Repo.Permission.CanWrite(unit.TypeCode) → 403

### Workflow Dispatch (ep-283):
- Write access to repo (implied by middleware)
- Additional check: workflow must not be disabled

## 7. The access Table — Materialized Permission Cache

The access table is the denormalized permission store:

| Operation | Endpoints |
|-----------|-----------|
| SELECT | ep-035, ep-064, ep-065, ep-066, ep-067, ep-172, ep-173, ep-174, ep-200, ep-206, ep-207, ep-208, ep-211, ep-254, ep-256, ep-333, ep-362, ep-368 |
| UPDATE | ep-063, ep-066, ep-067, ep-252, ep-253 |
| DELETE/INSERT | ep-331, ep-332 |
| DELETE | ep-076 |

Recalculation triggers:
- Adding/removing a collaborator (ep-252, ep-253)
- Adding/removing a team member (ep-062, ep-063)
- Adding/removing a repo from a team (ep-066, ep-067, ep-331, ep-332)
- Removing an org member (ep-076)

## 8. Special Permission Contexts

### Package Access (ep-200, ep-202, ep-206):
- Access mode determined by owner type:
  - **Org owner:** Check team permissions
  - **User owner:** Check if doer is owner or visibility is public/limited
- Write operations: ctx.Package.AccessMode < accessMode && !ctx.IsUserSiteAdmin() → 403

### Notification Access (ep-019, ep-023):
- GetIndividualUserRepoPermission called per notification to filter visible repos
- Users only see notifications for repos they have access to

### Repository Search (ep-362):
- No auth required, but results filtered by authentication
- Private repos only shown to authenticated users with access
- permission.HasAnyUnitAccess() filters results

### Self-or-Admin Pattern (ep-165 Token Creation):
- reqSelfOrAdmin middleware: authenticated user must be the target user OR a site admin

## 9. Complete Request Flow Diagram

Request arrives
    │
    ▼
[1] Authentication (reqToken / bearer / basic)
    │ → 401 if no valid auth (for protected endpoints)
    │
    ▼
[2] Token Scope Check
    │ → 403 if token lacks required scope
    │
    ▼
[3] Site Admin Check (bypass shortcut)
    │ → If IsAdmin=true, most checks pass automatically
    │
    ▼
[4a] Org Resolution (orgAssignment) — for org endpoints
    │ → 404 if org not found
    │
    ▼
[4b] Org Visibility Check (HasOrgOrUserVisible)
    │ → 404 if org not visible to doer
    │
    ▼
[4c] Org Permission Middleware (reqOrgOwnership / reqOrgMembership / reqTeamMembership)
    │ → 403/404 if insufficient org-level permission
    │
    ▼
[5a] Repo Resolution — for repo endpoints
    │ → 404 if repo not found
    │
    ▼
[5b] Permission Calculation (GetDoerRepoPermission)
    │   ├── Check owner (→ full access)
    │   ├── Check collaborator (→ collaboration.mode)
    │   ├── Check org teams (→ MAX(team.authorize) per unit)
    │   └── Check access table (→ pre-computed level)
    │
    ▼
[5c] Unit-Level Permission Check
    │ → 403 if user lacks required unit access
    │   (CanWrite, CanRead, HasAnyUnitAccess)
    │
    ▼
[6] Endpoint-Specific Business Rules
    │ → Various 4xx based on:
    │   - User blocks (403)
    │   - Repo archived (423)
    │   - Repo is mirror (403)
    │   - Feature disabled (400)
    │
    ▼
[7] ALLOW — Execute operation

## 11. Permission Recalculation

The access table is not queried in real-time from source-of-truth tables for every request. Instead, it's a pre-computed cache that gets recalculated when:

1. A collaborator is added/updated/removed (ep-252, ep-253)
2. A team member is added/removed (ep-062, ep-063)
3. A repo is added/removed from a team (ep-066, ep-067, ep-331, ep-332)
4. An org member is removed (ep-076 — deletes all access records)

The recalculation happens within database transactions to maintain consistency.
