## Step-by-Step Flow

### Step 1: HTTP Handler — repo.CreatePullRequest (controller)

- Parses the JSON request body (CreatePullRequestOption) containing: head, base, title, body, assignee, assignees, milestone, labels, due_date, reviewers, team_reviewers, allow_maintainer_edit
- **Validation:** Checks that head != base (returns 422 if equal)

### Step 2: parseCompareInfo (utility)

- Parses the compare parameter (head/base branch references)
- Resolves the head repository (may be a fork)
- Checks user permissions on the head repo
- **Git operation:** Gets compare info via git (commit comparison between head and base branches)
- **Validation:** Both base and head refs must be branches (not tags or commits) — returns 422 if not

### Step 3: issues_model.GetUnmergedPullRequest (repository)

- **Database:** SELECT on pull_request table — checks for existing unmerged PR with same head repo, base repo, head branch, and base branch
- Returns 409 if duplicate PR already exists

### Step 4: issues_model.GetLabelsInRepoByIDs (repository)

- **Database:** SELECT on label table (implied) — fetches label objects by the IDs provided in the request

### Step 5: issues_model.GetMilestoneByRepoID (repository)

- Fetches the milestone by repo ID if a milestone ID was provided in the request

### Step 6: issues_model.MakeIDsFromAPIAssigneesToAdd (repository)

- Resolves assignee usernames to user IDs
- **Database:** SELECT on user table — GetUserByID for each assignee (N+1 query pattern)

### Step 7: access_model.CanBeAssigned (repository)

- **Database:** SELECT on access/collaboration tables (implied) — verifies each assignee has access to the repository
- Called individually per assignee (N+1 pattern — documented performance issue)

### Step 8: pull_service.NewPullRequest (service) — Core Logic

This is the main service call that orchestrates the PR creation. It performs the following sub-operations:

1. Check blocked users — SELECT on blocked_user table; returns 403 if poster is blocked by repo owner
2. Check collaborator/member — Verifies PR creator is a collaborator, org member, or has write access to head repo; returns 403 if not authorized
3. Create issue + PR in transaction (database writes):
   - **INSERT into issue table** — Creates the issue record with title, content (body), poster ID, repo ID, milestone ID, due date
   - **INSERT into pull_request table** — Creates the PR record with head branch, base branch, head repo ID, base repo ID, linked to the issue
4. Add assignees — Writes assignee associations (implied INSERT into issue_assignees)
5. Git operation: Push to base repo ref — Pushes the head branch reference to the base repository's git refs (e.g., refs/pull/{index}/head). This happens outside the DB transaction.
6. Sync commit divergence — Calculates and stores the number of commits ahead/behind between head and base
7. Add code owners review — Reads CODEOWNERS file from the repository and automatically requests reviews from code owners

### Step 9: convert.ToAPIPullRequest (utility)

- Converts the internal issues_model.Issue + issues_model.PullRequest objects into the API response format (PullRequest JSON)
- Returns HTTP 201 with the serialized PR

## Resiliency Concerns

- **Non-atomic:** The git push to base repo ref happens after the DB transaction commits. If the git push fails, the PR exists in the database but without the git ref. Cleanup attempts to remove the git ref on failure (best-effort).
- **Cascading failure risk:** Git repository unavailability causes PR creation to fail with HTTP 500.
- **Performance issue (medium):** Assignee validation loops through each assignee individually calling GetUserByID and CanBeAssigned — should be batched.
