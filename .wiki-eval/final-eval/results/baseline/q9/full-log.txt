1. **Pool Configuration** (`modules/setting/database.go`):
   - `MaxOpenConns` defaults to 0 (unlimited)
   - `MaxIdleConns` defaults to 2
   - `ConnMaxLifetime` defaults to 3s for MySQL, 0 for others
   - These are applied in `models/db/engine_init.go` via `xe.SetMaxOpenConns()` and `xe.SetMaxIdleConns()`

2. **Connection Acquisition**: 
   - All database access goes through `db.GetEngine(ctx)` which returns either an existing session from context or creates a new `xormEngine.Context(ctx)` session
   - Transactions use `db.WithTx()` or `db.TxContext()` which calls `xormEngine.NewSession()` and `sess.Begin()`
   
3. **When pool is exhausted**:
   - Go's `database/sql` package (which xorm uses underneath) will **block** waiting for a connection when all connections are in use and MaxOpenConns is reached
   - The blocking will continue until either: a connection becomes available, or the context is cancelled
   - Since Gitea uses the request's context (passed through `xormEngine.Context(ctx)`), the blocking will be bounded by the HTTP request lifecycle
   - If the request context gets cancelled (client disconnects, or graceful shutdown), the blocked DB call will return `context.Canceled` or `context.DeadlineExceeded`
   - Without a timeout on the context, the request could block indefinitely waiting for a connection

4. **Error propagation path**:
   - Database operation fails → returns error
   - Caller (model/service layer) propagates error up
   - Router handler receives error
   - For API: `ctx.APIErrorInternal(err)` → logs error, returns HTTP 500 with JSON `{"message": "...", "url": "..."}`
   - For Web: `ctx.ServerError(msg, err)` → logs error, renders 500 template page
   - There's also a global panic recovery in `RequestContextHandler()` that catches any panics and renders 500

5. **ALL endpoints are affected** since they all share the same xorm engine (`xormEngine`). There's no per-endpoint pool isolation.

6. **No specific pool exhaustion handling**: Gitea doesn't have specific error handling for pool exhaustion. The error from `database/sql` (typically "context deadline exceeded" or blocking) is treated like any other database error.

## Key Observations

1. **No dedicated pool exhaustion handling** — Gitea treats this error the same as any other database error (generic 500).
2. **No per-request database timeout** — requests can block indefinitely waiting for a connection (bounded only by client disconnection or server shutdown).
3. **No retry logic at runtime** — retry logic (`DBConnectRetries`) only exists at startup in `routers/common/db.go` for initial engine initialization, not for per-request queries.
4. **No circuit breaker** — there's no mechanism to fail fast when the pool is saturated; all requests queue up.
5. **Health check is also affected** — `routers/web/healthcheck/check.go:104` calls `db.GetEngine(ctx).Ping()`, so it will correctly report `fail` status if it can't get a connection.[0m[0m[38;5;12m[1m✓ Created checkpoint 1
